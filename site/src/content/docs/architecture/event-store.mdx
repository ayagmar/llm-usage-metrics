The event store (`src/persistence/event-store-*.ts`) is a local SQLite **ledger**, not a disposable cache. It solves three problems at once: warm runs skip reparsing files that have not changed, usage from files that later disappear stays reportable through `--history`, and a file that merely moved is recognized by content so it never double counts. Because the ledger retains rows for departed files, deleting `events.db` deletes that retained history — you get a fresh ledger, not just a slower next run.

## Location and lifecycle

- **Default path**: `getDefaultEventStorePath()` resolves to `llm-usage-metrics/events.db` under the platform data root — `~/.local/share/llm-usage-metrics/events.db` on Linux and macOS when `XDG_DATA_HOME` is unset, `%LOCALAPPDATA%` on Windows. Older versions kept the ledger under the cache root, which users and cleanup tools clear; the first open of the default path (a report or `prune`) copies a ledger found there: a `VACUUM INTO` snapshot, hard-linked into place so concurrent first runs cannot overwrite each other. The old file is kept, because an older version may still write to it; delete it once you no longer run one. A `legacy-ledger-copied` marker beside the new ledger records the copy, so a later reset (deleting `events.db`) never re-imports the old file and its already-pruned history. `doctor` points at it until the copy happens. A custom `eventStore.path` or `LLM_USAGE_EVENT_STORE_PATH` never triggers the copy.
- **Relocate**: the `eventStore.path` config key, or `LLM_USAGE_EVENT_STORE_PATH` (the env var wins over config).
- **Disable**: `eventStore.enabled = false` in config, or `LLM_USAGE_EVENT_STORE=0`. Reports then parse everything live. With the store disabled, reports run without retained history; an explicit `--history` and `prune` fail with a message naming whichever setting disabled it: `--history requires the event store (unset LLM_USAGE_EVENT_STORE=0)` when the env var disabled it, or `--history requires the event store (set eventStore.enabled = true in config.toml)` when `eventStore.enabled = false` disabled it (and the matching message for `prune`). If the store is enabled but cannot be opened, a report warns and parses everything live, while an explicit `--history` fails with the open error. History is on by default (`--no-history` turns it off); by default it also skips sources the command line points at a custom directory, and its `History:` note appears only when departed files were added.
- **Migrations**: the schema version lives in a `meta` table. A store written by an older schema migrates in place on first open — the v1→v2 migration adds the content-hash column and backfills a hash per event, which can take seconds on large stores. The v3→v4 migration adds a column for one-hour cache writes; events stored before it count none until their file is reparsed (a file still on disk is, since the Claude parser version changed). A store with an unknown **newer** schema version is left untouched: opening throws `EventStoreSchemaVersionError` and the run continues with the store disabled instead of rebuilding tables.
- **Open failure**: if the store cannot be opened (or fails mid-run), the report still runs; the store is disabled for the rest of the run and a diagnostic is emitted on `stderr`: `Event store disabled after failure: <reason>`.

## Ingest and validity

The ledger keys one record set per `(source, file path)`: a row in `files` (fingerprint, skipped-row stats, ingest time) plus ordered rows in `events`. Ingest is replace-on-change: after a successful parse, the file's old event rows are deleted and the new ones inserted in a single transaction.

Stored events are reused only when dependency fingerprints match exactly. A fingerprint is the serialized list of a file's dependencies — the primary file first, plus any sidecar inputs the adapter declares via `getParseDependencies(filePath)` — each recorded as `{path, exists, size, mtimeMs}` (a missing sidecar is recorded as `exists: false`). Any difference in the serialized fingerprint is a store miss: the file is reparsed and its rows replaced. The fingerprint also carries a parser version, built from the shared event-normalization version and the adapter's `parserVersion`; bumping either re-parses unchanged files, so parser fixes reach events that were stored by an older release.

Report runs open the store **once** and share the handle across the pipeline: `buildUsageEventDataset` opens it before parsing, passes it to the adapter parse phase, reuses it for `--history`, and closes it after both (`prune` opens its own handle).

## Content hashes and move suppression

Every stored event carries a 16-hex-character SHA-256 content hash over its identity fields: source, session id, timestamp, model, provider, repo root, all five token counts plus total, cost mode, and cost. The one-hour cache-write count is left out: it only splits the cache-write count, so an event keeps its hash across the v4 upgrade. The hash deliberately excludes the file path, which is what makes move detection work: a moved file keeps the same hashes.

When `--history` classifies a departed file, it compares that file's multiset of content hashes against the data already being served (live discovered files, plus departed files already selected for replay). For a source whose files repeat each other's events (pi), a hash found in several live files counts as often as the file holding it most often, as reports count it. If every hash in the departed file is covered, the file's content lives on at another path — a move, rename, or copy — and the file is **suppressed** rather than replayed, so nothing double counts. Rows whose hash is `NULL` (un-normalizable rows kept by the v1→v2 migration) never suppress a file. A file with only *partial* overlap is replayed without the events already served: per hash, as many of its events as are already counted are left out. A matching hash covers the session id and timestamp, so it is the same event — for example, a pi fork's copy of a parent session that kept going after the fork. `prune --suppressed` still selects only whole-file suppression, so a partially served file is never pruned by it. `machine export` leaves out the same events, deciding on the events it sends, so another machine counts what this one reports.

## `--history` reads

`src/persistence/event-store-history.ts` serves `--history`:

1. It takes the run's successfully parsed sources and their discovered `(source, file)` pairs. Only successfully parsed sources participate — a failed source has an empty discovered set, so all its stored files would otherwise look departed.
2. Stored files for those sources that were **not** discovered this run and are also missing from disk are the departed set, classified oldest-ingested first with the move suppression above. A stored file that discovery skipped but that still exists (for example, outside a narrowed `--source-dir`) counts as live: it is neither replayed as history nor offered to `prune`. When a file's presence cannot be checked (for example, permission denied), history replays it so usage is never hidden, while `prune` keeps it so nothing is deleted without proof that the file is gone.
3. Events from non-suppressed departed files, less any already counted, are replayed and appended to their source's parse results **before** the provider/model/date filters, pricing, and aggregation — so report shapes are unchanged and history events flow through the exact same pipeline.

History reads never mutate the ledger: the classification writes only connection-local SQLite `TEMP` tables. Each history run reports its outcome as a diagnostic: `History: included N event(s) from M departed file(s) (K suppressed as moved or duplicated).`

## Prune

`llm-usage prune` deletes departed-file rows from the ledger. It requires at least one selector and is a dry run by default — without `--apply` it prints the candidate table and `Would delete N file(s) / M event(s). Re-run with --apply.`

- `--suppressed` selects departed files that history already suppresses as moved or duplicated — applying it never changes report output.
- `--departed-before YYYY-MM-DD` selects departed files whose newest event timestamp is strictly older than that UTC date.
- `--apply` deletes the selected files' rows in one transaction, runs `VACUUM`, truncates the WAL, and reports reclaimed bytes across the database, `-wal`, and `-shm` files.

Prune shares its classification logic (`classifyDepartedFiles`) with the history read path, so "suppressed" means exactly the same thing in both. Prune does not parse, so a live file stands in for a departed copy only while its stored entry matches its current fingerprint, as when a report last read it successfully. A file that failed to parse, changed since, or awaits a re-parse after an upgrade counts as present but not counted, so `--suppressed` keeps its departed copies until a report reads it again. With `--apply`, that check is repeated under the write lock, just before deleting.

## Operational notes

- The store runs in WAL journal mode, so `events.db-wal` and `events.db-shm` appear alongside `events.db`; opens use a 2-second busy timeout. To back up the ledger, copy all three files while no report is running.
- `LLM_USAGE_EVENT_STORE=0` and `LLM_USAGE_EVENT_STORE_PATH` are the per-run env overrides; the persistent equivalents are the `eventStore.enabled` and `eventStore.path` config keys.
- [Caching](/llm-usage-metrics/caching/) covers the user-facing tuning view of the store; [Configuration](/llm-usage-metrics/configuration/) documents the config keys.
