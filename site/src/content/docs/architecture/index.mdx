The repository holds two packages. `@ayagmar/agent-sessions` (`packages/core`) reads agent logs and turns them into normalized events. The `llm-usage-metrics` CLI (`src/`) stores, merges, prices, aggregates, and renders those events. The CLI imports the core package and its build bundles it, so `dist/index.js` carries both.

<PackageLayers />

## Core package

`packages/core/src` reads local files and has no runtime dependencies. It makes no network calls of its own: the pricing fetcher uses the `fetch` and the cache file its caller passes.

| Directory   | What lives there                                                                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sources/`  | One directory per source (17), the adapter contract (`source-adapter.ts`), parse diagnostics, fingerprints, multi-root and multi-directory discovery, JSON and SQLite readers |
| `registry/` | The adapter list in registry order, `createDefaultAdapters`, worker eligibility, and `readSources`                                                                            |
| `stream/`   | Async-iterable stages: `readEvents`, `collect`/`collectFile`, `pipe`, `kinds`, `since`/`until`, `bySession`, and read cursors                                                |
| `dedup/`    | The content hash and the repeated-across-files and copied-session stages                                                                                                      |
| `domain/`   | The event types and constructors, timestamp and provider normalization, active time                                                                                          |
| `pricing/`  | LiteLLM loading and cache file, model-name matching, the cost engine, overrides, retired prices, cache savings, `pricing` explain                                            |
| `utils/`    | File discovery, chunked reads, and the JSONL reader with byte and string prefilters                                                                                           |
| `otel/`     | OpenTelemetry GenAI attributes for events (experimental)                                                                                                                       |
| `internal/` | Helpers the CLI uses that are not part of the public API                                                                                                                       |

The package's exports map publishes `.`, `./registry`, `./otel`, `./internal`, and `./sources/<id>` for each source. [Library](/llm-usage-metrics/library/) documents the public API.

## A report run

<EventFlow />

Every report that reads usage builds its events through `buildUsageEventDataset` (`src/cli/build-usage-event-dataset.ts`) and prices them through `applyPricingToUsageEventDataset`:

1. **Discover.** Each selected adapter lists its files.
2. **Look up.** Each file's fingerprint is compared with the event store. A match serves the stored events and skips steps 3 and 4.
3. **Read.** The misses are parsed under one shared concurrency budget, on worker threads when a large claude, codex, or pi backlog justifies them.
4. **Store.** Fresh parses replace their files' stored events.
5. **Dedupe repeats.** For pi, an event repeated across files counts once.
6. **Merge.** History replays files that have left the disk (on unless `--no-history`), and other machines' cached events are merged in. A sync with other machines starts at the beginning of the run, alongside steps 1 to 5.
7. **Dedupe copies.** For claude, an event copied between sessions counts once.
8. **Filter.** Date window, provider, model, and repo.
9. **Price, aggregate, render.** Each report's builder prices the events, aggregates them its own way, and hands the result to its renderer.

[Parse pipeline](/llm-usage-metrics/architecture/parse-pipeline/) covers steps 1 to 5, [Event store](/llm-usage-metrics/architecture/event-store/) steps 2, 4, and history, [Dedup and cursors](/llm-usage-metrics/architecture/dedup-and-cursors/) steps 5 and 7, [Machine merge](/llm-usage-metrics/architecture/machine-merge/) step 6, and [Pricing pipeline](/llm-usage-metrics/architecture/pricing-pipeline/) step 9.

## Report definitions and runtime

`src/cli/report-definitions/report-definitions.ts` defines every report command, in this order: `summary` (the default command), `hourly`, `daily`, `weekly`, `monthly`, `projects`, `compare`, `efficiency`, `optimize`, `trends`, `session`, `blocks`, `value`, `wrapped`, `events`, `pricing`, `statusline`, `doctor`, and `prune`. A definition names the command, its shared option profile (`shared-report-options.ts`), and its examples. The same metadata registers the Commander command, builds the root help examples, and generates the [CLI reference](/llm-usage-metrics/cli-reference/), so option descriptions are written once.

`config` (`init`, `path`, `show`), `schema`, `completion`, `machine` (`add`, `list`, `remove`, `export`), and `sync` are registered directly in `src/cli/create-cli.ts`.

`src/cli/report-runtime/report-lifecycle.ts` runs every report the same way: it validates the output format, builds the report data, builds the share file when `--share` is set, emits diagnostics on stderr, writes the share file, and prints the report on stdout.

| Command                                | Builder                                       | Renderer                                         |
| -------------------------------------- | --------------------------------------------- | ------------------------------------------------ |
| `summary`                              | `buildSummaryData`                            | `renderSummaryReportWithNotes`                   |
| `hourly`, `daily`, `weekly`, `monthly` | `buildUsageData`                              | `renderUsageReportWithNotes`                     |
| `projects`                             | `buildProjectsData`                           | `renderProjectsReportWithNotes`                  |
| `compare`                              | `buildCompareData`                            | `renderCompareReportWithNotes`                   |
| `efficiency`                           | `buildEfficiencyData`                         | `renderEfficiencyReportWithNotes`                |
| `optimize`                             | `buildOptimizeData`                           | `renderOptimizeReportWithNotes`                  |
| `trends`                               | `buildTrendsData`                             | `renderTrendsReport`                             |
| `session`                              | `buildSessionData`                            | `renderSessionReport`                            |
| `blocks`                               | `buildBlocksData`                             | `renderBlocksReportWithNotes`                    |
| `value`                                | `buildValueData`                              | `renderValueReportWithNotes`                     |
| `wrapped`                              | `buildWrappedData`                            | `renderWrappedReportWithNotes`                   |
| `pricing`                              | `run-pricing-report.ts` (reads no usage)      | `renderPricingReport`                            |
| `doctor`, `prune`                      | `run-doctor-report.ts`, `run-prune-report.ts` | `renderDoctorText`, `renderPruneReportWithNotes` |

`events` and `statusline` have their own runners (`run-events-report.ts`, `run-statusline.ts`): `events` exports the priced events as JSONL, CSV, or OTLP traces or metrics, and `statusline` prints one line for a status bar. `--share` builds its own dataset; see [Share report](/llm-usage-metrics/architecture/share-report/).

`aggregateUsage` keeps per-model breakdowns by default; `trends`, `optimize`, and `efficiency` turn them off. `src/render/unicode-table.ts` lays out rows from explicit metadata (`periodKey`, and `rowKind`: `detail`, `combined`, or `total`), so sorting and separators stay deterministic without the table knowing report types. Given a terminal width and a `fit`, it abbreviates values and then hides columns before it lists rows as labelled values.

## Invariants

- Deterministic ordering for periods, sources, models, projects, and machines.
- Report body on stdout, diagnostics on stderr; `--json` and `--markdown` output is data only.
- Normalization happens once, in the core constructors; see [Event model](/llm-usage-metrics/architecture/event-model/).
- An adapter's events depend only on its file, its declared dependencies, and its `parserVersion`, so stored events never go stale silently.
- Incomplete pricing stays visible in output (`~`, `-`, warnings, or incomplete flags).
