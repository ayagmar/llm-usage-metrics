This page started in February 2026, when `llm-usage` and `ccusage` were both TypeScript programs running on Node.js. ccusage 20.0.0 (May 2026) replaced its TypeScript code with a Rust binary. Its npm package is now a small Node launcher that starts the native binary for your platform. The direct comparison below is therefore Node against native code, with ccusage's launcher included because its package executable is the launcher. The `npx` scenario adds npm's package resolution on top.

All numbers below were measured on 2026-10-20 with 8 timed runs per cell, using ccusage 20.0.37 and the released `llm-usage` 0.12.1. ccusage is ahead on Codex, by about 1.7x in both application states. On Claude Code the two are level in fresh application state and llm-usage is ahead in warmed state. llm-usage is ahead on the warm monthly terminal check.

## Direct-process results

These cells invoke the built `llm-usage` entry and ccusage's installed package executable directly. They include process startup and captured JSON output, but exclude shell package-manager launchers such as `npx`.

### codex: `daily --json` (8 runs each)

| Tool                                                                          | Application state | Median (s) | Mean (s) | Min (s) | Max (s) |
| ----------------------------------------------------------------------------- | ----------------- | ---------: | -------: | ------: | ------: |
| `ccusage codex daily --no-offline --timezone UTC --json`                      | fresh             |      0.197 |    0.196 |   0.192 |   0.202 |
| `ccusage codex daily --offline --timezone UTC --json`                         | warmed            |      0.060 |    0.060 |   0.058 |   0.063 |
| `llm-usage daily --all --source codex --timezone UTC --json`                  | fresh             |      0.345 |    0.347 |   0.339 |   0.354 |
| `llm-usage daily --all --source codex --timezone UTC --json --pricing-offline` | warmed            |      0.103 |    0.103 |   0.101 |   0.105 |

From median runtime, ccusage was 1.76x faster in fresh application state and 1.71x faster in warmed application state.

### claude: `daily --json` (8 runs each)

| Tool                                                                           | Application state | Median (s) | Mean (s) | Min (s) | Max (s) |
| ------------------------------------------------------------------------------ | ----------------- | ---------: | -------: | ------: | ------: |
| `ccusage claude daily --no-offline --timezone UTC --json`                      | fresh             |      1.086 |    1.088 |   1.047 |   1.151 |
| `ccusage claude daily --offline --timezone UTC --json`                         | warmed            |      0.541 |    0.544 |   0.527 |   0.566 |
| `llm-usage daily --all --source claude --timezone UTC --json`                  | fresh             |      1.099 |    1.098 |   1.071 |   1.131 |
| `llm-usage daily --all --source claude --timezone UTC --json --pricing-offline` | warmed            |      0.351 |    0.349 |   0.338 |   0.358 |

From median runtime, the two were level in fresh application state (ccusage 1.01x faster) and llm-usage was 1.54x faster in warmed application state.

A second full run of each scenario gave medians within 3% of every cell above.

These are runtime comparisons of similar report commands, not byte-for-byte output-equivalence claims. The tools use different output schemas and normalization rules. On this snapshot both tools reported the same number of days for each source. Their grand totals agreed within 0.06% for Codex and within 0.01% for Claude Code, for both tokens and cost.

## The `npx` launcher scenario

The usual shell commands do not have equivalent launch paths: `llm-usage` is already installed, while `npx ccusage@<version>` starts npm, resolves the package, and then runs the ccusage launcher, which starts the native binary. This monthly terminal scenario uses the same stable Codex snapshot and the pinned ccusage version:

| Command                                                    | Launch path                      | Median (s) | Mean (s) | Min (s) | Max (s) |
| ---------------------------------------------------------- | -------------------------------- | ---------: | -------: | ------: | ------: |
| `llm-usage monthly --per-model-columns --source codex`     | installed command                |      0.101 |    0.101 |   0.095 |   0.105 |
| `ccusage codex monthly`                                    | package executable (launcher)    |      0.149 |    0.150 |   0.141 |   0.161 |
| `npx --yes ccusage@20.0.37 codex monthly`                  | npm + launcher + native binary   |      0.592 |    0.588 |   0.561 |   0.600 |

From median runtime, the installed `llm-usage` command was 1.48x faster than ccusage's package executable and 5.86x faster than the `npx` command. `npx` added about 0.44 s to ccusage.

The `llm-usage` row runs `dist/bin.js`, the entry the installed command uses, with its default event store, so after the warm-up it reads parsed events from the store. ccusage has no equivalent store and reads the logs on every run. Both report the full history (five months on this snapshot).

Each command received one untimed warm-up, then 8 timed runs in rotating order, so no command always ran first. Output was discarded through non-TTY pipes, and the system timezone plus default online pricing and update behavior were left in place. ccusage 20.0.37 was already in npm's package cache before the timed `npx` runs.

The `llm-usage` update check had a fresh cached answer during these runs, which is the usual case: the cache lasts an hour. When the cache is stale, the check waits at most 50 ms after the report before giving up, and a fetch it gives up on does not refresh the cache. On this machine the npm registry took about 0.3 s to answer, so with a stale cache every run of this short command paid the wait: the `llm-usage` median rose to 0.190 s. A longer command, such as a report over the Claude Code logs, gave the fetch time to finish and refreshed the cache.

## What the application states mean

- **Fresh application state:** a new `XDG_CACHE_HOME` and `XDG_CONFIG_HOME` for every timed run, live pricing, and `LLM_USAGE_EVENT_STORE=0` for llm-usage. This is not disk-cold: both corpora were read during setup, and the OS filesystem page cache was not flushed.
- **Warmed application state:** one live setup run populates each tool's pricing cache and llm-usage's event store. Timed runs then use offline pricing (`--offline` or `--pricing-offline`) and reuse that application state.
- ccusage does not expose an event ledger equivalent to llm-usage's SQLite store; “warmed” does not imply that both tools cache parsed source events in the same way.

## Dataset scope

| Corpus | Files                                  | Size on disk |
| ------ | -------------------------------------- | ------------ |
| codex  | 166 JSONL session files                | ≈ 287 MiB    |
| claude | 1,822 JSONL files (projects + subagents) | ≈ 5.30 GiB   |

The source trees were copied to a read-only snapshot immediately before the run, so active sessions could not grow between samples.

Codex had compressed 153 of its 166 rollouts to `.jsonl.zst` (95.5 MiB on disk). ccusage reads those files; `llm-usage` 0.12.1 does not, and skips them. To time both tools on the same data, the snapshot holds those rollouts decompressed to plain `.jsonl`, which is what the table above measures. On the compressed tree, `llm-usage` would read 13 files and report a small part of the Codex history.

This is a different corpus and machine from the July 2026 baseline (1,168 Codex files of ≈ 1.77 GiB, 271 Claude Code files of ≈ 178.8 MiB), so its runtimes are not comparable with these.

## Methodology

- 8 timed runs per cell. The four cells rotate execution order each run, so every cell occupies every position twice.
- Both tools use UTC, isolated application cache/config directories, and the same stable source snapshot.
- Inherited `LLM_USAGE_*` overrides are removed. The warmed llm-usage event store is explicitly enabled and placed inside the temporary benchmark root; fresh-state runs explicitly disable it.
- Fresh-state cells use live pricing. Warmed-state cells use pricing populated by one live setup run and then run offline.
- The OS filesystem page cache is not flushed. No true disk-cold claim is made.
- Direct-process cells exclude npm/npx/pnpm launcher overhead. ccusage's own Node launcher is part of its package executable, so its cells include it.
- llm-usage gets `LLM_USAGE_SKIP_UPDATE_CHECK=1` in the direct-process comparison. ccusage exposes no equivalent update-check switch.

## Engineering notes: the fresh Codex path

On the July 2026 Codex corpus (1,168 files, ≈ 1.77 GiB), a fresh run took 8.7 s before the parse-pipeline work and 1.527 s after it. The mechanisms, in pipeline order:

1. Byte prefilters and a buffer-based JSONL reader (`packages/core/src/utils/read-jsonl-objects.ts`) skip irrelevant lines before any JSON parsing.
2. A per-timezone local-date window cache for period bucketing (`src/utils/time-buckets.ts`) avoids repeated date math per event.
3. An event-store warm read path serves already-parsed events.
4. A worker-thread parse pool (`src/cli/parse-worker-pool.ts`) parses large JSONL files in parallel.

## Synthetic baseline

`scripts/benchmark-baseline.mjs` times the built CLI over a generated pi and codex corpus (200,000 lines per source over 4 files, 399,984 events), with a temp `HOME` and the store, pricing and update check pinned. It measures what is cheap to repeat: a cold run with the store off, a warm `daily`, a statusline tick, a growing JSONL file, and a statusline tick where most files are older than its 53-week window (`statusline-aged`).

0.11.0 and 0.12.1 were compared with it on 2026-10-20 on one machine (AMD Ryzen 9 9950X3D, 32 logical CPUs, 62.2 GiB RAM, Linux 7.2.11, Node.js v24.21.0). Each round started with the 1-minute load average below 2.0 (1.4–1.9) and it was 2.1–2.4 when a round ended. Two serial rounds alternated the versions (0.11.0 then 0.12.1, then 0.12.1 then 0.11.0), with 5 timed runs per scenario per round. Both versions ran the 0.12.1 script. Each cell gives the two rounds' medians, and the change compares their means:

| Scenario          |    0.11.0 (s) |  0.12.1 (s) | Change |
| ----------------- | ------------: | ----------: | -----: |
| `cold`            | 1.173 / 1.190 | 1.263 / 1.265 |  +7.0% |
| `warm`            | 0.665 / 0.678 | 0.534 / 0.529 | −20.8% |
| `statusline`      | 0.857 / 0.795 | 0.499 / 0.504 | −39.3% |
| `active-jsonl`    | 1.031 / 1.031 | 0.561 / 0.560 | −45.6% |
| `statusline-aged` | 0.278 / 0.264 | 0.204 / 0.203 | −24.9% |

The store-off cold run is about 7% slower in 0.12.1, in both rounds. Peak RSS was lower in 0.12.1 in every scenario: `cold` 386–402 MB against 416–432 MB, `warm` 381 MB against 417–419 MB, `statusline` 348–360 MB against 440 MB, and `active-jsonl` 364–365 MB against 440–445 MB. `active-jsonl` gains the most because 0.12.1 reads only the lines appended to a pi file that grew. No source in this corpus reaches the parse-worker threshold, so the worker-pool change behind the real-log cold gain below does not show here. These are synthetic files with dense usage lines, so they show relative change between builds, not what real logs cost.

## Real logs (maintainer's machine)

The synthetic corpus above has dense usage lines. Real logs are mostly conversation text, so 0.11.0 and 0.12.1 were also compared on the maintainer's own logs on 2026-10-20, on the same machine (Node.js v24.21.0). Each run started with the 1-minute load average below 2.0 (1.3–1.97); it reached 3.9 during the cold runs.

- The logs are the read-only snapshot used above: Claude Code, Codex (rollouts decompressed), pi, Gemini and OpenCode.
- Each run uses a temp `HOME` that links to those log directories, plus temp cache, data and config directories, `TZ=Europe/Paris` and `LLM_USAGE_SKIP_UPDATE_CHECK=1`.
- "Cold" is one `statusline` on an empty event store. One untimed `summary --json` then fills the pricing cache. "Warm" runs reuse the store the cold run filled; each warm cell is the median of 3 runs.
- The two versions alternate over 3 rounds, each round with a fresh store. Each cell gives the range over the rounds.

| Run                   |        0.11.0 |      0.12.1 |
| --------------------- | ------------: | ----------: |
| Cold `statusline`     |   5.87–6.24 s | 3.42–3.55 s |
| Cold peak RSS         |    694–711 MB  |  761–826 MB |
| Warm `statusline`     |    598–636 ms |  419–435 ms |
| Warm `summary --json` |    597–629 ms |  516–533 ms |
| Warm `daily --json`   |    333–343 ms |  300–312 ms |
| Warm `tools --json`   | not in 0.11.0 | 0.66–0.69 s |
| Event store size      |         87 MB |       69 MB |

A warm `daily --json` is about 10% faster in 0.12.1. The 0.12.1 store is smaller although it also holds tool calls and messages.

Most of the cold gain comes from parsing Claude Code and pi files on the worker pool. The cost is memory, because a cold run keeps several parse workers busy at once. Cold runs happen only on the first run and after a parser update; a lower `parseWorkers` lowers the peak. Warm runs read unchanged files from the event store, parse only files that changed, and read only the appended lines of a claude, pi or qwen file that grew.

## Reproduce it

Build the current checkout and install the pinned ccusage version into a scratch directory, so `npx` is not part of the timing:

```bash
pnpm run build
npm install --prefix "$HOME/.cache/ccusage-bench" ccusage@20.0.37
CCUSAGE_BIN="$HOME/.cache/ccusage-bench/node_modules/.bin/ccusage"
"$CCUSAGE_BIN" --version
node scripts/perf-production-benchmark.mjs --runs 8 --scenario all --ccusage-bin "$CCUSAGE_BIN"
```

Stop Codex and Claude while the benchmark runs, or point `HOME` at a stable snapshot containing `.codex/sessions` and `.claude/projects`. Decompress any `.jsonl.zst` Codex rollouts in the snapshot first, or the two tools read different data. Replace the pinned ccusage version only when intentionally creating a new baseline. The script also accepts `--json-output <path>` and `--markdown-output <path>` to export artifacts.

The script does not run the `npx` scenario. To repeat it, time the three commands from its table with the same `HOME`, one untimed warm-up each first.

Results are machine-, dataset-, command-, and launcher-specific. Re-run the exact scenario you care about before drawing a broader conclusion.
