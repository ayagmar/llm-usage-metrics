This page publishes absolute runtimes for `llm-usage` and `ccusage` on stable snapshots of real local data. The result depends on what is timed: ccusage wins every cell of the counterbalanced direct-process comparison, by 1.3x to 2.4x. With default settings at the shell, ccusage refetches pricing on every run while llm-usage reuses its cached pricing, which reverses a monthly terminal run; launching ccusage through `npx` adds about half a second more. All numbers below were measured on 2026-10-08 with 8 timed runs per cell.

## Direct-process results

These cells invoke the built `llm-usage` entry and ccusage's installed package executable directly. They include process startup and captured JSON output, but exclude shell package-manager launchers such as `npx`. llm-usage runs with `--all` so both tools report the full history.

### codex — `daily --json` (8 runs each)

| Tool                                                                           | Application state | Median (s) | Mean (s) | Min (s) | Max (s) |
| ------------------------------------------------------------------------------ | ----------------- | ---------: | -------: | ------: | ------: |
| `ccusage codex daily --no-offline --timezone UTC --json`                       | fresh             |      0.220 |    0.203 |   0.148 |   0.228 |
| `ccusage codex daily --offline --timezone UTC --json`                          | warmed            |      0.053 |    0.054 |   0.052 |   0.055 |
| `llm-usage daily --all --source codex --timezone UTC --json`                   | fresh             |      0.289 |    0.303 |   0.263 |   0.351 |
| `llm-usage daily --all --source codex --timezone UTC --json --pricing-offline` | warmed            |      0.088 |    0.088 |   0.086 |   0.091 |

From median runtime, ccusage was 1.32x faster in fresh application state and 1.65x faster in warmed application state.

### claude — `daily --json` (8 runs each)

| Tool                                                                            | Application state | Median (s) | Mean (s) | Min (s) | Max (s) |
| ------------------------------------------------------------------------------- | ----------------- | ---------: | -------: | ------: | ------: |
| `ccusage claude daily --no-offline --timezone UTC --json`                       | fresh             |      0.255 |    0.246 |   0.180 |   0.260 |
| `ccusage claude daily --offline --timezone UTC --json`                          | warmed            |      0.089 |    0.089 |   0.085 |   0.092 |
| `llm-usage daily --all --source claude --timezone UTC --json`                   | fresh             |      0.623 |    0.623 |   0.571 |   0.670 |
| `llm-usage daily --all --source claude --timezone UTC --json --pricing-offline` | warmed            |      0.125 |    0.126 |   0.121 |   0.131 |

From median runtime, ccusage was 2.44x faster in fresh application state and 1.40x faster in warmed application state.

These are runtime comparisons of similar report commands, not correctness or byte-for-byte output-equivalence claims. The tools use different output schemas and normalization rules.

## The shell path: installed command, package executable, and `npx`

The commands people type do not behave the same way by default. `llm-usage` starts Node on its built entry and reuses its cached pricing (and its ledger) on a repeat run; `ccusage` fetches live pricing on every run unless it gets `--offline`; and `npx ccusage@latest` first starts npm, resolves the package, and prepares its execution environment. We timed a monthly terminal report on the same Codex snapshot:

| Command                                                | Launch path                     | Median (s) | Mean (s) | Min (s) | Max (s) |
| ------------------------------------------------------ | ------------------------------- | ---------: | -------: | ------: | ------: |
| `llm-usage monthly --per-model-columns --source codex` | built entry, warmed ledger      |      0.096 |    0.096 |   0.089 |   0.101 |
| `ccusage codex monthly`                                | package executable, live prices |      0.159 |    0.147 |   0.117 |   0.174 |
| `ccusage codex monthly --offline`                      | package executable, cached      |      0.054 |    0.054 |   0.053 |   0.057 |
| `npx --yes ccusage@20.0.26 codex monthly`              | npm + ccusage (package cached)  |      0.628 |    0.618 |   0.569 |   0.647 |

With default settings `llm-usage` was 1.65x faster than the ccusage executable and 6.5x faster than the `npx` form. That comes from pricing, not parsing: given cached prices with `--offline`, ccusage was 1.78x faster than `llm-usage`, in line with the warmed direct-process cells above. Use launcher-inclusive timing to judge the one-off `npx` experience, and the direct-process cells to compare the tools themselves.

This launcher check is an observed shell-path comparison, not the counterbalanced benchmark above. Each command received one untimed warm-up followed by 8 sequential timed runs on the stable snapshot; commands were grouped by row, output was discarded through non-TTY pipes, `LLM_USAGE_*` variables were removed, and the system timezone plus default online pricing and update-check behavior were left in place. The `--offline` row was timed separately right after the others, with the same procedure. ccusage 20.0.26 was already in npm's package cache before its direct and `npx` rows, and `llm-usage` ran as `node dist/index.js`, which is what the installed `llm-usage` bin starts. The build was master at `7d1aba7`, just before the 0.9.0 release; the code these reports run (parsing, pricing, the event store, daily and monthly aggregation) is unchanged in 0.9.0.

## What the application states mean

- **Fresh application state:** a new `XDG_CACHE_HOME` and `XDG_CONFIG_HOME` for every timed run, live pricing, and `LLM_USAGE_EVENT_STORE=0` for llm-usage. This is not disk-cold: both corpora were read during setup, and the OS filesystem page cache was not flushed.
- **Warmed application state:** one live setup run populates each tool's pricing cache and llm-usage's event store. Timed runs then use offline pricing (`--offline` or `--pricing-offline`) and reuse that application state.
- ccusage does not expose an event ledger equivalent to llm-usage's SQLite store; “warmed” does not imply that both tools cache parsed source events in the same way.

## Dataset scope

| Corpus | Files                     | Size on disk |
| ------ | ------------------------- | ------------ |
| codex  | 136 JSONL session files   | ≈ 235 MiB    |
| claude | 431 JSONL files           | ≈ 362 MiB    |

The source trees were copied to a snapshot on a RAM-backed filesystem immediately before the run, so the active sessions could not grow between samples, and `HOME` pointed at that snapshot for both tools.

## Methodology

- 8 timed runs per cell. The four cells rotate execution order each run, so every cell occupies every position twice.
- Both tools use UTC, isolated application cache/config directories, and the same stable source snapshot.
- Inherited `LLM_USAGE_*` overrides are removed. The warmed llm-usage event store is explicitly enabled and placed inside the temporary benchmark root; fresh-state runs explicitly disable it.
- Fresh-state cells use live pricing. Warmed-state cells use pricing populated by one live setup run and then run offline.
- The OS filesystem page cache is not flushed. No true disk-cold claim is made.
- Direct-process cells exclude npm/npx/pnpm launcher overhead. The separate monthly table intentionally includes `npx` in its third row.
- llm-usage gets `LLM_USAGE_SKIP_UPDATE_CHECK=1` in the direct-process comparison. ccusage exposes no equivalent update-check switch.

## Engineering notes: the fresh Codex path

On the July 2026 baseline (a 1.77 GiB Codex corpus on an Intel Core Ultra 9 185H), the parse-pipeline work took a fresh Codex run from 8.7 s to 1.527 s. Today's numbers come from a different machine and corpus, so they are not a before-and-after comparison. The mechanisms, in pipeline order:

1. Byte prefilters and a buffer-based JSONL reader (`src/utils/read-jsonl-objects.ts`) skip irrelevant lines before any JSON parsing.
2. A per-timezone local-date window cache for period bucketing (`src/utils/time-buckets.ts`) avoids repeated date math per event.
3. An event-store warm read path serves already-parsed events.
4. A worker-thread parse pool (`src/cli/parse-worker-pool.ts`) parses large JSONL files in parallel.

## Reproduce it

Build the current checkout and resolve the exact ccusage version without timing `npx` itself:

```bash
pnpm run build
CCUSAGE_BIN=$(npx --yes --package=ccusage@20.0.26 sh -c 'command -v ccusage')
"$CCUSAGE_BIN" --version
node scripts/perf-production-benchmark.mjs --runs 8 --scenario all --ccusage-bin "$CCUSAGE_BIN"
```

Stop Codex and Claude while the benchmark runs, or point `HOME` at a stable snapshot containing `.codex` and `.claude`. Replace the pinned ccusage version only when intentionally creating a new baseline. The script also accepts `--json-output <path>` and `--markdown-output <path>` to export artifacts.

Results are machine-, dataset-, command-, and launcher-specific. Re-run the exact scenario you care about before drawing a broader conclusion.
